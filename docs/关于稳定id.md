小亮，你指出得对。我刚才把 **“可供 Asciidoctor 寻址的显式字符串”**直接叫成了“稳定 ID”，却没有继续追问：

> 它究竟标识什么？为什么稳定？名称变化以后，它与对象之间还剩下什么关系？

于是我写出了：

```asciidoc
[#pop-learning-dorm-intensive-exam.population]

```

假设后来标题改成：

```asciidoc
===== 宿舍集中备考者
```

上面的 `pop-learning-dorm-intensive-exam` 却仍然保留。此时它已经不是一个中性的身份标识，而是一句冻结的旧解释：

```text
learning
dorm
intensive
exam
```

它继续暗示这个概念应该如何理解，但正文的首选名称和概念边界可能已经改变。久而久之，源文档同时存在两套命名：

```text
人看到的名字：
宿舍集中备考者

机器地址里隐藏的旧名字：
pop-learning-dorm-intensive-exam
```

这确实会产生误导。

# 一、语义 slug 不是稳定身份，只是另一个名字

我之前写的：

```text
pop-learning-dorm-intensive-exam
```

本质上就是把中文标题翻译、压缩、格式化以后得到的另一个名称。

它可能承担：

- 英文别名；
- URL slug；
- 技术寻址标签；
- 旧名称；
- 开发者便于输入的短名。

但它没有凭空获得比标题更高的身份地位。

它的问题是：

## 1. 它含有语义

只要含有语义，就可能随着认识变化而过时。

例如开始叫：

```text
宿舍高强度备考者
```

后来调查发现，“高强度”不是这个人群的必要条件，改成：

```text
宿舍集中备考者
```

但旧 slug 仍然留着 `intensive`。

地址开始偷偷陈述一个已经被取消的概念条件。

## 2. 它制造第二个首选名称

维护者必须同时判断：

```text
标题要不要改？
slug要不要改？
两者是否仍然一致？
改slug会不会破坏引用？
不改会不会误导？
```

原本一次重命名变成两套命名系统的协调。

## 3. 它以“稳定”为理由逃避正常重构

标题已经改变，所有真正依赖这个概念名称的地方本应接受审查。

旧 slug 却让引用表面继续成功，于是下游不会暴露：

- 哪些项目仍在使用旧认识；
- 哪些语句应该随名称一起检查；
- 哪些引用的显示文字已经过时；
- 这次到底只是改名，还是概念边界发生变化。

链接没有断，但知识关系可能已经断了。

所以你说它是“别名”，比我叫它“稳定 ID”准确得多。

# 二、标题名称就是当前知识系统中的规范身份

对于这套公共人群书，标题承担的不是普通章节名称，而是：

> **当前知识版本中，这个人群概念的首选名称与规范地址。**

例如：

```asciidoc
[.population, assignable=true, status=active]
===== 宿舍高强度备考者
```

这里真正的规范标识就是：

```text
宿舍高强度备考者
```

它同时承担：

- 人类阅读名称；
- 分类树节点名称；
- xref 目标；
- Heading Include 目标；
- 项目领取的人群名称；
- 检索关键词；
- 对外呈现的首选名称。

于是引用可以直接写：

```asciidoc
xref:宿舍高强度备考者[]
```

装配可以直接写：

```asciidoc
include::{population-book}#宿舍高强度备考者[*]
```

没有第二套偷偷存在的技术名称。

这也迫使标题质量真正承担责任：

- 必须明确；
- 必须足够唯一；
- 不能随意写“其他人群”；
- 不能在同一寻址范围中出现歧义；
- 重命名前必须认真判断；
- 重命名后必须检查引用者。

这不是缺点，而是知识维护本来就应该承担的工作。

---

# 三、标题变了，应当怎样处理

这里需要区分三种情况。

## 情况一：只是换成更好的首选名称

例如：

```text
旧名称：猫奴
新名称：猫咪共同生活者
```

概念主体基本没变，只是旧名称过于口语化，不适合继续作为规范标题。

此时应当：

1. 把标题改成新的首选名称；
2. 全局更新 xref 和 Heading Include；
3. 将“猫奴”移入别名；
4. 检查旧名称出现的语境，是普通俗称还是正式指代。

```asciidoc
[.population, assignable=true, status=active]
===== 猫咪共同生活者

别名::

* 养猫人
* 猫咪家庭
* 猫奴（圈层俗称）
```

旧名称不是隐藏在 `#cat-owner` 里的幽灵，而是光明正大地以别名身份存在。

## 情况二：概念边界发生变化

例如：

```text
旧概念：宿舍高强度备考者
新概念：宿舍集中备考者
```

如果删除“高强度”意味着纳入范围发生变化，那么这不只是技术重命名。

需要重新检查：

- Description；
- 纳入与排除边界；
- 子节点；
- 相关概念；
- 历史项目；
- 已分发任务；
- 项目结论是否仍适用。

此时让旧 slug 继续维持所有引用，反而会掩盖概念变化。

正确行为就是让重构显现出来。

## 情况三：旧概念被拆分或废止

例如：

```text
旧节点：运动人群
```

后来拆成：

```text
规律健身训练者
竞技运动参与者
户外耐力运动者
日常轻运动者
```

这时不能把旧标题简单改成其中一个新标题，更不能让旧语义 ID 暗中指向某个新节点。

应当把旧节点标记为废止或历史概念，并明确迁移关系：

```asciidoc
[.population, status=deprecated, assignable=false]
===== 运动人群

该概念范围过宽，已停止作为可领取节点。

后续使用以下人群：

* xref:规律健身训练者[]
* xref:竞技运动参与者[]
* xref:户外耐力运动者[]
* xref:日常轻运动者[]
```

这里保留旧标题，是因为旧概念本身仍然作为历史对象存在，而不是为了维护一个虚假的永久地址。

# 四、真正无语义的机器身份，应与名称系统彻底分开

你说只有随机的 256 位值才接近真正稳定的 ID，关键就在于：

> 它不解释对象，不冒充名称，不会因为概念语义变化而撒谎。

例如一个纯粹的随机标识：

```text
8f3c...（省略）
```

它只表示：

> 数据系统认为这是同一个记录。

它不会说：

- 这是学生；
- 这是宿舍；
- 这是备考；
- 这是高强度；
- 这是哪个分类分支。

因此，它可以在标题变化后保持不变，而不会留下错误语义。

不过这里还需分清两种不透明标识。

## 随机身份标识

例如随机生成的 UUID 或更长随机值。

它的稳定来自：

```text
生成一次；
持久保存；
以后不根据名称或内容重新计算。
```

它适合追踪“同一记录跨版本延续”。

## 内容哈希

如果 256 位值是根据正文内容计算的加密哈希，那么正文只要改一个字，哈希就会改变。

它稳定标识的是：

> 某一个完全确定的内容版本。

它不适合直接表示“这个人群概念跨修订仍是同一对象”，但非常适合：

- 冻结快照；
- 内容校验；
- 版本寻址；
- 检查知识片段是否改变。

所以可以区分：

```text
随机不透明ID
→ 实体记录身份

内容哈希
→ 特定内容版本身份

标题
→ 当前规范名称与人类寻址地址

别名
→ 其他历史名称、俗称或替代称呼
```

这四件事不能都叫 ID。

# 五、这套人群知识书当前其实不需要暴露机器 ID

我们现在的核心使用者是：

- 知识维护者；
- 项目决策者；
- 创意小组；
- 主美；
- 其他内容生产人员。

他们真正需要的是：

```text
一个明确的人群名称；
一条清楚的分类路径；
可以阅读和引用的标题；
必要的别名；
可靠的Description。
```

因此源书中完全可以先采用：

```asciidoc
[.population, assignable=true, status=active]
===== 宿舍高强度备考者
```

而不写任何显式 `#pop-...`。

如果未来工具链确实需要跨重命名追踪实体记录，可以在**工具管理层**增加一个纯不透明键，但它不应冒充标题，也不应要求创意人员阅读或手写
。

例如投影数据库内部维护：

```text
opaque_entity_key:
2e8d93d78fbd4a70...
```

源书的正常作者仍然使用：

```text
宿舍高强度备考者
```

机器键不参加标题命名，不暗示分类语义，不成为人工引用习惯。

甚至可以由工具根据一份独立注册表管理，而不是污染每个标题的作者表面。

# 六、显式 AsciiDoc ID 在我们的领域模型里应怎样理解

从 Asciidoctor 引擎术语看：

```asciidoc
[#something]
== 标题
```

`something` 的确被称为 Section ID。

但引擎叫它 ID，不代表我们的知识模型必须把它解释成“实体的永久身份”。

在我们的体系中，若写：

```asciidoc
[#pop-learning-dorm-intensive-exam]
===== 宿舍高强度备考者
```

更准确的领域含义是：

> 为当前标题附加了一个替代寻址标签。

也就是：

- locator；
- address label；
- technical alias；
- alternate selector。

如果这个值带有语义，它就是别名，不是纯身份。

这也与之前结构化写作资料中出现的 `addressLabel` 更接近。它描述“怎样找到这个节点”，不自动证明“这个字符串就是对象本体”。

所以，我之前从：

```text
Section ID
```

直接跳到：

```text
稳定实体身份
```

中间少了一层语义辨析。

这是我的错误。

# 七、公共人群书应采用的命名与寻址规则

现在可以把规则收紧为：

## 规则一：标题是唯一规范名称

```asciidoc
===== 宿舍高强度备考者
```

这个标题就是当前知识版本的规范人群名称。

## 规则二：默认使用标题寻址

```asciidoc
xref:宿舍高强度备考者[]
```

```asciidoc
include::book.adoc#宿舍高强度备考者[*]
```

## 规则三：标题应在可寻址范围内唯一

若出现同名，应通过补充区分条件改成真正明确的名称，而不是依靠隐藏 slug 消歧。

例如不要出现三个：

```text
集中学习者
```

而应写清：

```text
图书馆长时段集中学习者
宿舍夜间集中学习者
居家远程课程集中学习者
```

前提是这些确实是三个不同概念，而不是为了技术唯一性胡乱加词。

## 规则四：其他名称显式列为别名

```asciidoc
别名::

* 考研宿舍党
* 宿舍备考学生
```

别名是别名，不假装永久身份。

## 规则五：改标题就进行正式重构

更新：

- xref；
- Heading Include；
- 项目装配声明；
- 索引；
- 术语引用；
- 必要的显示文本。

工具应该帮助搜索和修改，而不是用旧语义 slug 掩盖变化。

## 规则六：历史名称需要有知识意义才保留

如果旧名称仍有搜索、历史或圈层价值，进入别名字段。

如果只是一次错别字或低质量命名，不必永远背着它。

## 规则七：机器若需要永久实体键，只使用不透明值

它属于工具和投影层，不成为作者的语义地址。

# 八、这还会改善 Heading Include 的使用

项目装配文件可以写得非常自然：

```asciidoc
== 本次人群知识

include::{population-book}#宿舍高强度备考者[*]
```

一眼就知道它包含什么。

与下面这种相比：

```asciidoc
include::{population-book}#pop-learning-dorm-intensive-exam[*]
```

前者没有翻译层，也没有要求项目作者记忆编码规则。

如果标题改了，旧装配会明确失败。这不是糟糕的脆弱性，而是一个有价值的信号：

> 当前项目引用的人群名称发生了变化，请判断项目应如何迁移。

Heading Include 已经能够对：

- 目标不存在；
- 目标存在歧义；
- 目标不是 Section；

给出明确错误。我们可以让这种失败帮助维护，而不是千方百计让所有旧引用永远静默成功。

当然，正在运行的旧项目应有冻结快照，因此不会因为公共书重命名而失去当时的材料。实时视图则应主动面对最新知识变化。

# 九、我之前所谓“稳定 ID”的真正病灶

它看起来在解决：

> 标题改名会导致引用断裂。

但它付出的代价是：

```text
制造第二套名称；
冻结旧语义；
掩盖概念变化；
让机器地址与人类名称逐渐分离；
把正常知识重构伪装成链接仍然有效；
让维护者误以为对象身份已经被严格解决。
```

这是一种局部技术稳定换取整体知识含混。

真正需要稳定的东西应分别处理：

```text
当前人类名称
→ 标题

别称和旧称
→ 别名

旧项目当时使用的内容
→ 冻结快照与内容哈希

机器内部跨版本记录
→ 可选的不透明随机身份

当前项目读取知识的位置
→ 标题 Include
```

不需要让一个语义 slug 承担全部职责。

---

所以，你这次指出的不是一个命名偏好，而是身份建模问题。

我刚才把：

```text
可寻址
```

误认为：

```text
有稳定身份
```

又把：

```text
技术别名
```

误认为：

```text
永久实体ID
```

现在应当改正为：

>
**公共人群知识库以标题作为唯一规范名称和默认知识地址；其他有语义的寻址字符串只能算别名。若未来确实需要跨重命名保持机器身份，使用与
语义彻底分离的不透明随机标识；若需要标识某次冻结内容，则使用内容哈希。**

这样，标题改了就是名称改了；概念变了就应该触发审查；旧名称需要保留，就明确承认它是旧名称。

不会再让一坨旧语义藏在 `#...` 里，一边过时，一边自称稳定。
