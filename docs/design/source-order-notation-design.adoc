== 摘要

本文定义一套用于长期书稿源文件的源文件编排号制度。

源文件编排号是写在源文件路径表面的内部排序 notation。它服务作者和维护者观察、插入和局部调整源文件，不进入读者可见标题，也不作为 cross reference 的目标。

该制度分离四类对象：

* 源文件编排号承担内部维护排序。
* 显示标题承担读者可见语义。
* 稳定引用 ID 承担可依赖引用地址。
* role、rel、索引词和术语表承担结构语义。

该制度不是新的知识分类法，也不是 Dewey Decimal Classification 的本地复刻。它借鉴既有知识组织、记录管理、信息架构和文档工程中的成熟原则，把可扩展 notation、稳定引用、显示标签和结构语义放回各自层位。

== 问题域

长期书稿源文件同时面对四类消费者：

* 作者需要在文件树中观察写作顺序。
* 维护者需要在中间插入、移动和调整章节。
* 工具链需要从源文件生成目录、网页、PDF 或其他投影。
* 读者和外部文档需要稳定引用已发表或可依赖的内容位置。

连续自然序号能让初始文件树清楚，例如 `01-topic/`、`02-topic/`、`03-topic/`。该写法的维护成本出现在中间插入时：在 `01` 和 `02` 之间插入一个同级单元时，若仍要求编号连续，后续同级文件必须连锁重命名。连锁重命名会带来 include 路径修改、版本历史噪声、外部路径依赖风险和人工检查成本。

显示标题中的自然序数也会制造混合层位。发布工具已经能生成读者可见的 part、chapter 或 section 编号；源标题再手写“第一部”“第二章”等序数，会让维护位置进入读者语义面，并在重排后产生额外修改。

稳定引用 ID 与源文件排序码混用会扩大破坏面。章节移动本应只改变维护位置；若引用 ID 包含排序码，章节移动会同时改变公共引用契约。

因此，当前对象不是“换一种好看的编号”，而是定义一种源文件组织制度，使内部排序、显示标题、稳定引用和结构语义不再互相冒充。

== 需求推导

本节使用需求工程中的 `Domain ∧ Specification ⊨ Requirements` 关系表达制度推导。该关系来自 Zave 与 Jackson 对领域事实、规约和需求满足关系的区分。本文采用该关系作为对象分层工具，不把它当作形式化证明系统。

=== Domain

书稿源文件处在以下领域事实中：

* 源文件按文件系统路径组织。
* 文件系统路径影响编辑器、终端、搜索、版本控制和人工观察。
* 发布编号由构建工具根据源文档结构生成。
* cross reference 依赖稳定目标。
* 书稿在长期维护中会发生中间插入和局部重排。
* Git 记录文件路径变化，连锁重命名会增加审查成本。
* 结构化书稿需要同时服务读者阅读和工具链投影。

=== Requirements

在上述领域事实下，源文件组织制度需要满足以下需求：

* 局部插入：中间新增同级单元时，不要求重命名无关后续单元。
* 自然排序：文件树按普通字典序即可呈现可读维护顺序。
* 显示干净：读者可见标题不携带内部维护序号。
* 引用稳定：cross reference 目标不随源文件维护位置变化。
* 语义清楚：身份、关系、术语和索引继续由专门结构表达。
* 工具轻量：制度由普通路径、显式 include 和普通 AsciiDoc 语法承载。
* 可审查：维护者能判断一个编号是否承担了越界职责。

=== Specification

满足这些需求的可控规约是：在源文件路径中使用稀疏的源文件编排号；将该编排号限定为内部排序 notation；禁止它进入显示标题、稳定引用 ID 和结构语义标记。

该规约与领域事实共同作用后，可以推出需求满足：

* 稀疏编号提供中间空位，因此支持局部插入。
* 固定宽度数字前缀支持文件树自然排序。
* 标题不手写自然序数，因此输出编号由工具统一生成。
* anchor 不含编排号，因此引用目标不随维护位置变化。
* role、rel、索引词和术语表继续表达语义，因此排序码不承载内容本体。

== 知识来源

该制度来自成熟知识传统的适配，不是原创分类法。

=== Dewey Decimal Classification

OCLC 的 Dewey Decimal Classification 术语表把 classification 描述为用于安排知识的逻辑系统，并包含用于标识对象在分类中位置的 notation。该术语表还说明 DDC 中的 hierarchy 从一般到具体排列，notation 的长度通常对应更具体的层级。

本制度借鉴 DDC 的三点：

* notation 可以服务位置表达。
* notation 可以支持有序排列。
* notation 可以为继续细分保留结构空间。

本制度不借用 DDC 的学科分类表。书稿源文件编排号不是 000-999 知识分类，也不把文件所属主题固定在跨馆藏分类体系中。它只表达当前书稿源文件的内部维护位置。

=== 记录管理

ISO 15489-1:2016 定义记录创建、捕获和管理的概念与原则，并明确涉及 records、records metadata、records systems、policies、assigned responsibilities、monitoring、records requirements 和 records controls。该标准还说明记录管理适用于不同结构、形式、业务环境和技术环境中的记录。

本制度借鉴记录管理的制度视角：长期文档不是随手命名的文本堆，而是需要元数据、责任、控制规则和持续管理的记录对象。

该借鉴不把普通书稿源文件提升为正式档案系统。它只说明：一旦源文件进入长期协作和发布链路，路径表面就承担维护责任，命名制度应被明确定义。

=== 稳定 URI 与引用契约

Tim Berners-Lee 的 W3C 文档 _Cool URIs don't change_ 将 URI 稳定性作为 Web 文档维护中的长期责任，并强调许多实现细节会变化，但 URI 应当保持稳定。该文档还指出，文件移动不应直接迫使公共标识变化，抽象 URI 空间可以映射到底层文件系统现实。

本制度借鉴稳定 URI 思想：公共引用目标不应依赖易变的维护位置。AsciiDoc 源文件中的 stable anchor 承担引用契约；源文件编排号只承担维护排序。路径可以服务 include 和本地维护，但不应替代显式 anchor。

=== 信息架构

信息架构传统区分组织系统、标签系统、导航系统和检索系统。该区分说明：内容如何被组织、显示标签如何命名、用户如何导航、用户如何查找，不是同一个对象。

本制度据此分离：

* 源文件编排号属于组织系统。
* 显示标题属于标签系统。
* include 顺序和目录属于导航投影。
* anchor、索引词和术语表属于引用与检索入口。

=== 技术文档结构

Diátaxis 把技术文档组织为 tutorial、how-to guide、reference 和 explanation 等面向用户需求的文档形式，并把 documentation architecture 与用户需求联系起来。该框架提醒文档结构应围绕读者和维护者的任务组织，而不是围绕作者的内部施工过程组织。

本制度据此要求：读者可见标题表达内容语义，不表达源文件维护位置。内部编排号只出现在维护表面。

== 设计对象定义

=== 源文件编排号

源文件编排号是写在源文件路径表面的内部排序 notation。它服务作者和维护者观察、插入和局部调整源文件，不进入读者可见标题，也不作为 cross reference 目标。

=== 显示标题

显示标题是读者在正文、目录和输出页面中看到的标题文本。显示标题表达内容语义，不承担源文件维护排序。

=== 稳定引用 ID

稳定引用 ID 是写在 AsciiDoc anchor 中的显式引用地址。稳定引用 ID 承担 cross reference 契约，不包含源文件编排号。

=== 内部路径

内部路径是源文件在书稿目录中的文件系统位置。内部路径服务 include、编辑、搜索和版本控制，不自动成为公共引用契约。

=== 导航投影

导航投影是工具链从源文件结构生成的目录、网页导航、PDF 书签或其他读者可见顺序表达。导航投影可以使用源文件顺序，但不应暴露内部编排号。

=== 结构语义

结构语义由 role、rel、索引词、术语表、显式 anchor 和正文约定表达。源文件编排号不表达结构语义。

== 规约

=== 编排号表面

源文件编排号写在目录名或文件名前部，并与语义 slug 使用连字符分隔。

目录表面：

[source,text]
----
100-topic/
200-topic/
300-topic/
----

文件表面：

[source,text]
----
010-opening.adoc
020-main-flow.adoc
030-closing.adoc
----

=== 大单元编号

part、volume section 或其他同级大单元使用三位十进制编排号。标准间隔为 100。

[source,text]
----
100-topic/
200-topic/
300-topic/
----

在两个既有大单元之间插入新大单元时，使用中间空位。

[source,text]
----
100-topic/
150-new-topic/
200-topic/
----

=== 小单元编号

chapter 或其他容器内同级小单元使用三位十进制编排号。标准间隔为 10。

[source,text]
----
010-opening.adoc
020-main-flow.adoc
030-closing.adoc
----

在两个既有小单元之间插入新小单元时，使用中间空位。

[source,text]
----
010-opening.adoc
015-new-context.adoc
020-main-flow.adoc
----

=== 编排号作用域

小单元编排号在所属容器内有效。不同容器可以重复使用 `010`、`020`、`030`。

目录层级已经表达所属容器；文件名不重复写入上级编排号。

=== 辅助结构文件

结构性辅助文件不参与章节排序。绑定在容器上的导言、局部属性文件或局部片段文件使用下划线前缀。

[source,text]
----
_partintro.adoc
_attributes.adoc
----

下划线前缀表达“该文件服务所在容器的结构”，不表达读者可见顺序。

=== 显示标题规则

显示标题不写内部编排号，也不写由发布工具生成的自然序号。

允许：

[source,asciidoc]
----
= 源文件组织
== 稳定引用
----

不允许：

[source,asciidoc]
----
= 第一部：源文件组织
== 第 01 章：稳定引用
----

=== 稳定引用规则

显式 anchor 使用语义 ID，不包含源文件编排号。

允许：

[source,asciidoc]
----
[#stable-reference]
== 稳定引用
----

不允许：

[source,asciidoc]
----
[#010-stable-reference]
== 稳定引用
----

=== include 顺序

显式 include 清单或导航清单承担输出顺序的权威投影。源文件编排号服务维护者观察，但不替代入口文件中的显式结构。

=== 局部重排

当局部区间耗尽时，只对该局部区间重排。局部重排不改变显示标题和稳定引用 ID。

局部重排属于维护操作，不是内容语义变更。

== 非目标与边界

源文件编排号不是 Dewey Decimal Classification 的本地复刻。

源文件编排号不是学科分类号。

源文件编排号不是读者可见章节编号。

源文件编排号不是版本号。

源文件编排号不是 stable anchor。

源文件编排号不是 role、rel、索引词或术语表的替代物。

源文件编排号不是自动导航生成器。

源文件编排号不保证内容质量。它只降低源文件维护排序的摩擦。

== 质量标准

一套源文件编排号制度成立，需要满足以下标准：

局部插入::
  在常见中间插入场景下，新文件可以使用相邻编号之间的空位，不触发后续同级文件连锁重命名。

自然排序::
  文件树按普通字典序排列时，维护顺序清楚。

层位分离::
  编排号、显示标题、stable anchor 和结构语义各自承担单一职责。

引用稳定::
  内容移动或局部重排不要求修改 cross reference 目标。

工具兼容::
  制度由普通文件名、普通目录名和普通 AsciiDoc include 承载。

可审查::
  维护者能从规则判断一个编号是否越界承担了显示编号、语义分类或引用契约。

可迁移::
  该制度能应用到不同书稿，不依赖某一本书的私有章节名称。
