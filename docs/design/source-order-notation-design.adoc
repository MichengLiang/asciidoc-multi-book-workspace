== 摘要

源文件编排号是写在源文件路径表面的排序符号。它使书稿源文件在文件树中保持可读顺序，并为中间插入保留位置。

该制度分离四个对象：

* 编排号表达源文件顺序。
* 标题表达正文语义。
* 显式 ID 表达引用地址。
* role、rel、索引词和术语表表达结构语义。

该制度借鉴 Dewey Decimal Classification 中 notation 与层级排列的思想，借鉴记录管理对文件控制和责任的要求，借鉴稳定 URI 对公共引用的要求，借鉴信息架构对组织、标签、导航和检索的分层。它不建立新的知识分类法。

== 问题域

书稿源文件同时服务写作、维护、构建和引用。

写作者需要在文件树中看见章节顺序。维护者需要在既有章节之间插入新章节。构建工具需要按照入口文件生成读者可见的目录和章节编号。读者和外部文档需要依赖稳定引用地址。

连续自然序号能表达初始顺序。`01-topic/`、`02-topic/`、`03-topic/` 在初始目录中清楚，但它们把相邻位置全部占满。在 `01` 和 `02` 之间插入同级单元时，连续编号制度要求后续单元改号。改号会连带修改 include 路径、版本历史、审查范围和潜在外部路径依赖。

显示标题中的自然序数也会扩大维护面。发布工具已经能生成读者可见编号；源标题再手写“第一部”“第二章”等序数，会把维护位置写入正文语义。章节重排后，标题文本也必须跟着修改。

引用 ID 与排序号混用会破坏引用稳定性。章节移动本应只改变维护位置；若 anchor 含排序号，移动会改变 cross reference 目标。

当前问题是源文件组织制度问题。该制度需要同时保持本地可观察、局部可插入、输出可编号、引用可稳定。

== 需求推导

需求工程中的 `Domain ∧ Specification ⊨ Requirements` 关系区分领域事实、可控规约和需求满足。本文用该关系说明制度推导。

=== Domain

书稿源文件处在以下领域事实中：

* 文件系统路径影响编辑器、终端、搜索、版本控制和人工观察。
* AsciiDoc 入口文件通过显式 include 表达书稿结构。
* 发布编号由构建工具根据源文档结构生成。
* cross reference 需要稳定目标。
* 长期书稿会发生中间插入和局部重排。
* Git 会记录路径变化；连锁重命名会增加审查成本。
* 结构化书稿需要同时服务读者阅读和工具链投影。

=== Requirements

源文件组织制度需要满足以下需求：

局部插入::
  中间新增同级单元时，不要求重命名无关后续单元。

自然排序::
  文件树按普通字典序排列时，维护顺序清楚。

输出独立::
  读者可见编号由构建工具生成，不由源文件名前缀或标题文本手写。

引用稳定::
  cross reference 目标不随源文件维护位置变化。

语义分层::
  标题、role、rel、索引词和术语表继续表达内容语义；排序符号只表达源文件顺序。

工具轻量::
  制度由普通目录名、普通文件名和普通 AsciiDoc include 承载。

可审查::
  维护者能判断一个文本表面是否承担了错误职责。

=== Specification

满足这些需求的规约如下：

* 源文件路径使用固定宽度的稀疏编排号。
* 大单元使用 `100-`、`200-`、`300-` 这样的三位编排号。
* 小单元在所属容器内使用 `010-`、`020-`、`030-` 这样的三位编排号。
* 中间插入使用相邻编排号之间的空位。
* 正文标题只写语义标题。
* 显式 anchor 只写稳定引用 ID。
* include 清单继续表达书稿投影顺序。

该规约与领域事实共同作用后满足上述需求。稀疏编号提供插入空间；固定宽度编号提供自然排序；标题和 anchor 不含编排号，因此输出编号和引用地址不被维护位置污染。

== 知识来源与推理职责

本制度来自成熟知识传统的适配。引用坐标只在参与当前推理时进入本文。

=== Dewey Decimal Classification

OCLC 的 Dewey Decimal Classification 术语表把 classification 描述为安排知识的逻辑系统，并把 notation 描述为代表对象所属分类的符号。DDC 的 hierarchy 从一般到具体排列；notation 的长度通常对应更具体的层级。

DDC 在本文中承担一个推理职责：说明数字 notation 可以表达有序位置，并通过可继续细分的形式容纳增长。

本制度只借鉴该职责。书稿源文件编排号不采用 DDC 的学科分类表，不把源文件主题映射到 000-999 分类，也不建立跨书稿的公共知识分类。

=== 记录管理

ISO 15489-1:2016 处理 records、records metadata、records systems、policies、assigned responsibilities、monitoring、records requirements 和 records controls。该标准说明记录管理适用于不同结构、形式、业务环境和技术环境中的记录。

记录管理在本文中承担一个推理职责：说明长期文件需要明确的控制规则和责任表面。源文件路径不是随手命名的私有草稿；进入长期协作和发布链路后，路径表面会影响维护、审查和引用。

本制度不把书稿源文件等同于正式档案系统。它只借鉴记录管理对文件控制的基本要求。

=== 稳定 URI

Tim Berners-Lee 的 W3C 文档 _Cool URIs don't change_ 把 URI 稳定性视为 Web 文档维护中的长期责任。该文指出，组织、软件和文件系统都会变化；公共标识应避免跟随易变实现细节移动。

稳定 URI 在本文中承担一个推理职责：说明公共引用地址应与易变维护位置分离。AsciiDoc 书稿中的显式 anchor 承担稳定引用职责；源文件编排号承担维护排序职责。

=== 信息架构

信息架构传统区分组织系统、标签系统、导航系统和检索系统。该区分说明：内容如何组织、标题如何标记、读者如何导航、内容如何检索，不是同一个对象。

信息架构在本文中承担一个推理职责：支持本制度把路径编排、显示标题、include 顺序、anchor、索引词和术语表分开处理。

=== 技术文档结构

Diátaxis 把技术文档结构与读者需求联系起来，并区分 tutorial、how-to guide、reference 和 explanation 等文档形式。

Diátaxis 在本文中承担一个推理职责：提醒文档结构应服务读者任务。内部维护编号不应进入读者标题；读者标题应表达内容语义。

=== 需求工程

Zave 与 Jackson 的需求工程关系 `Domain ∧ Specification ⊨ Requirements` 在本文中承担一个推理职责：防止从偏好的文件名样式直接跳到规约。源文件编排号制度必须从领域事实和需求推出。

== 术语

源文件编排号::
  写在源文件路径表面的排序符号。

语义 slug::
  编排号之后的可读名称，例如 `topic`、`opening`、`main-flow`。

显示标题::
  读者在正文、目录和输出页面中看到的标题文本。

稳定引用 ID::
  写在 AsciiDoc anchor 中的显式引用地址。

内部路径::
  源文件在书稿目录中的文件系统位置。

导航投影::
  工具链从源文件结构生成的目录、网页导航、PDF 书签或其他读者可见顺序表达。

结构语义::
  由 role、rel、索引词、术语表、显式 ID 和正文约定表达的文档意义。

== 规约

=== 编排号表面

源文件编排号写在目录名或文件名前部。编排号与语义 slug 使用连字符分隔。

[source,text]
----
100-topic/
010-opening.adoc
----

=== 大单元编排

part、volume section 或其他同级大单元使用三位编排号。初始间隔为 100。

[source,text]
----
100-topic/
200-topic/
300-topic/
----

在两个既有大单元之间插入新大单元时，使用中间空位。

[source,text]
----
100-topic/
150-new-topic/
200-topic/
----

=== 小单元编排

chapter 或其他容器内同级小单元使用三位编排号。初始间隔为 10。

[source,text]
----
010-opening.adoc
020-main-flow.adoc
030-closing.adoc
----

在两个既有小单元之间插入新小单元时，使用中间空位。

[source,text]
----
010-opening.adoc
015-new-context.adoc
020-main-flow.adoc
----

=== 编排号作用域

小单元编排号在所属容器内有效。不同容器可以重复使用 `010`、`020`、`030`。

目录层级表达所属容器；文件名不重复写入上级编排号。

=== 辅助结构文件

绑定在容器上的导言、局部属性文件或局部片段文件使用下划线前缀。

[source,text]
----
_partintro.adoc
_attributes.adoc
----

下划线前缀表达该文件服务所在容器的结构。

=== 显示标题

显示标题写语义名称。

[source,asciidoc]
----
= 源文件组织
== 稳定引用
----

发布编号由构建工具生成。

=== 稳定引用

显式 anchor 使用语义 ID。

[source,asciidoc]
----
[#stable-reference]
== 稳定引用
----

=== include 顺序

显式 include 清单或导航清单承担输出顺序的权威投影。文件名前缀服务本地观察；入口文件继续表达书稿结构。

=== 局部重排

局部区间耗尽时，只重排该局部区间。局部重排不改变显示标题和稳定引用 ID。

== 边界

源文件编排号只表达源文件顺序。

它不承担以下职责：

* 读者可见章节编号。
* 学科分类号。
* 版本号。
* stable anchor。
* role、rel、索引词或术语表。
* 内容质量判断。

== 健康度量

健康的源文件编排号制度满足以下指标。每项指标按 0、1、2 计分。

[cols="1,2,2,2", options="header"]
|===
|指标 |0 |1 |2

|插入成本
|中间插入会触发后续同级文件连锁重命名。
|常见插入有空位，密集区间需要较多局部调整。
|常见插入只新增文件和入口 include。

|层位分离
|排序号进入标题、anchor 或语义标记。
|大部分分离，个别文本需要解释。
|排序号、标题、anchor 和结构语义各自独立。

|自然排序
|文件树顺序与阅读顺序无稳定关系。
|文件树需要少量人工解释。
|普通字典序即可呈现维护顺序。

|引用稳定
|移动章节会改变引用目标。
|引用目标大体稳定，少数目标依赖路径。
|引用目标使用语义 anchor，不依赖编排号。

|输出清洁
|读者标题出现内部维护编号。
|读者标题偶尔出现维护痕迹。
|读者标题只表达内容语义。

|规则可审查
|维护者无法判断编号是否越界。
|维护者需要查阅多个位置才能判断。
|单独阅读规则即可判断编号职责。
|===

健康阈值：总分不低于 10，且“层位分离”和“引用稳定”均不得低于 2。

优秀阈值：总分为 12，且新增章节或说明文本中没有无职责排除句、作者过程句和帮助页式填充句。

== 公共文本度量

制度文本进入书稿或设计文档前，按以下指标审查。

句子职责::
  每个句子只承担一个主要职责：定义、表面、解释规则、结构弹性、来源职责、边界或验收。

信号密度::
  每个段落至少包含一个可执行或可判断的对象规则。只表达姿态、安抚或作者过程的段落不进入正文。

负面边界比例::
  排除句只出现在边界段落。核心定义段落不使用排除句建立对象身份。

例子位置::
  例子只跟随规则，不替代规则。

语体一致::
  面向短书稿的章节使用短句、表面写法和直接规则。面向设计文档的章节可以展开来源和推导，但来源必须承担推理职责。
