== Abstract

`create-asciidoc-multi-book-workspace` is an npm initializer for complete AsciiDoc multi-book workspaces.
The initializer creates a user-owned workspace with seven sample books, a catalog, shared assets, explicit AsciiDoc dependencies, and one editable local build script.

This repository is the maintainer source for that initializer.
It contains TypeScript initializer source, user runtime source, the default workspace template, maintainer tests, the sample contract, and release-boundary checks.

== Object Boundary

=== Published Object

The published npm package is named `create-asciidoc-multi-book-workspace`.
Its command is:

[source,console]
----
pnpm create asciidoc-multi-book-workspace my-books
----

npm users can run:

[source,console]
----
npm create asciidoc-multi-book-workspace@latest my-books
----

The package is an initializer.
It creates files in the target directory and does not remain as a dependency of the generated workspace.

=== Generated Workspace

The generated workspace is a standalone AsciiDoc multi-book project.
It contains:

[source,text]
----
README.md
catalog.adoc
package.json
.gitignore
tools/adoc-books.mjs
books/00-book-anatomy
books/01-starter-book
books/02-multipart-monograph
books/03-technical-book-workflow
books/04-reference-manual
books/05-upper-volume
books/06-lower-volume
shared/attributes.adoc
shared/images/workspace-map.svg
----

The generated workspace does not contain maintainer-only files:

[source,text]
----
.github/
test/
src/
dist/
DESIGN.adoc
scripts/
----

The generated workspace owns its local runtime script.
`tools/adoc-books.mjs` is visible, editable, replaceable, and removable by the user.

=== Maintainer Repository

The maintainer repository contains:

[source,text]
----
src/
  create.ts
  init-workspace.ts
  template-manifest.ts
  runtime/adoc-books.mts
templates/default-workspace/
test/
.github/
README.md
DESIGN.adoc

----

`templates/default-workspace/` is the single source of truth for generated workspace content.
The repository root does not contain a second sample source under `books/`, `catalog.adoc`, or `shared/`.

`src/runtime/adoc-books.mts` is the source for the user runtime script.
The TypeScript build emits `dist/runtime/adoc-books.mjs`, and the initializer copies that file into generated workspaces as `tools/adoc-books.mjs`.

== Template Workspace Contract

=== Template Source

`templates/default-workspace/` is a complete user workspace template.
It contains the seven sample books, `catalog.adoc`, shared assets, the user README, `package.json.template`, and `gitignore.template`.

`package.json.template` renders to the generated `package.json`.
`gitignore.template` renders to `.gitignore`.
The template file names remain template-specific so the generated workspace receives ordinary project file names.

=== User package.json

The generated `package.json` directly lists the AsciiDoc toolchain:

[source,json]
----
{
  "scripts": {
    "build": "node tools/adoc-books.mjs build",
    "check": "node tools/adoc-books.mjs check",
    "clean": "node tools/adoc-books.mjs clean"
  },
  "devDependencies": {
    "@asciidoctor/reducer": "1.1.2",
    "asciidoctor": "2.2.9",
    "asciidoctor-kroki": "0.18.1"
  }
}
----

The initializer package is not listed in the generated workspace.
The user can inspect and manage the AsciiDoc dependencies directly.

=== Seven Sample Books

The default workspace contains these sample books:

`00-book-anatomy`::
  A complete book-structure specimen covering frontmatter, body structure, parts, and backmatter.

`01-starter-book`::
  A minimal ordinary book suitable as a copying starting point.

`02-multipart-monograph`::
  A single book that demonstrates `part` and `partintro` structure.

`03-technical-book-workflow`::
  A technical writing sample with diagrams, code includes, book-local assets, and shared assets.

`04-reference-manual`::
  A reference-style book with decision tables, path rules, xref patterns, and glossary material.

`05-upper-volume`::
  An independent upper volume with its own book entry and a stable anchor used in examples.

`06-lower-volume`::
  An independent lower volume that demonstrates cross-volume writing conventions by literal example.

=== Sample Independence

Every default sample book is independently removable.
A user can delete any one `books/<book-id>/` directory, remove the matching entries from `catalog.adoc`, and run:

[source,console]
----
pnpm run check
----

The check must pass after that operation.

Default sample books must not create real incoming cross-book dependencies on each other.
Book-to-book teaching material uses book IDs, paths, prose, or literal examples instead of executable cross-book xref macros.

Catalog links are the workspace navigation surface.
They are the only default links from `catalog.adoc` to sample book entries, and each sample must have catalog entries that can be removed without editing another sample book.

=== Cross-Book Xref Teaching

Cross-book xref syntax is taught as literal source text.
Default samples do not contain executable cross-book xrefs such as:

[source,asciidoc]
----
xref:../other-book/book.adoc#stable-anchor[Target]
----

Instead, samples use separated literal forms such as:

[source,asciidoc]
----
xref + : + ../other-book/book.adoc#stable-anchor[Target]
----

This preserves the teaching surface without creating a real dependency between default samples.

The user runtime still validates real cross-book xrefs.
If a user writes an executable xref to a missing `.adoc` file or missing anchor, `pnpm run check` must fail.

== Initializer Behavior

The initializer accepts one target path.
Missing target arguments print usage and fail.

Target handling rules:

* A missing target directory is created.
* An existing empty target directory is used.
* An existing non-empty target directory is rejected by default.
* `--force` overwrites fixed template output paths and does not delete unknown user files.

The initializer writes all template files, renders `package.json.template`, renders `gitignore.template`, copies the built runtime script to `tools/adoc-books.mjs`, and prints:

[source,text]
----
Created AsciiDoc multi-book workspace in <target>

Next:
  cd <target>
  pnpm install
  pnpm run build

Open:
  build/html/index.html
----

The generated package name is derived from the target directory basename and normalized to a safe npm package name.

== User Runtime Contract

=== Commands

`tools/adoc-books.mjs` supports:

[source,console]
----
node tools/adoc-books.mjs build
node tools/adoc-books.mjs check
node tools/adoc-books.mjs clean
----

The generated `package.json` exposes these commands as:

[source,console]
----
pnpm run build
pnpm run check
pnpm run clean
----

=== Build Outputs

`build` creates:

[source,text]
----
build/adoc/catalog.adoc
build/adoc/books/<book-id>.adoc
build/html/index.html
build/html/catalog.html
build/html/books/<book-id>/book.html
build/html/shared/images/
build/html/books/<book-id>/assets/
----

The build expands includes to single-file ADOC outputs, renders catalog HTML, renders each book HTML, copies shared images, copies book-local assets, injects a catalog home link into book HTML, writes the root HTML index, checks local HTML resources, and checks the workspace contract.
Diagram blocks render as Kroki image URLs by default, so ordinary builds do not depend on the Kroki service at build time.
When `ADOC_BOOKS_FETCH_DIAGRAMS=1` is set, the runtime asks Kroki to fetch diagram images into the local HTML output.

`check` runs the same complete validation path as `build`.
It is allowed to rebuild generated outputs.

`clean` deletes `build/` and no source files.

=== Workspace Contract Checks

The runtime checks the current workspace, not the official sample set.
It validates:

* `catalog.adoc` exists.
* Each `books/*/book.adoc` entry has `:doctype: book`.
* Catalog book links point to existing current books.
* Existing current books are listed in the catalog.
* Executable xrefs to `.adoc` files point to existing files.
* Executable xrefs with anchors point to explicit anchors.
* Generated HTML local `href` and `src` resources exist.

The runtime does not require all seven official sample books to remain present.
The official seven-book requirement belongs to maintainer tests only.

=== Cheap Performance Rules

The user runtime uses one Node process for the full build.
It uses Asciidoctor.js in process through `require("asciidoctor")()`.
It does not depend on a global `asciidoctor` executable.

The runtime registers `@asciidoctor/reducer` in process.
It loads `asciidoctor-kroki` only when current `.adoc` sources contain supported diagram blocks.
If diagram blocks exist and `asciidoctor-kroki` cannot be loaded, the runtime reports that the workspace contains diagram blocks and needs the Kroki dependency or needs those blocks removed.

The runtime does not implement content hashing, watch mode, deep incremental graphs, or a custom cache system.
It preserves HTML output directories for books that still exist so fetched Kroki SVG files can be reused when `ADOC_BOOKS_FETCH_DIAGRAMS=1` is used.
It deletes HTML output directories for books that no longer exist so removed books do not remain in generated output.

== Maintainer Tests

Maintainer tests are repository-only.
They are not copied into generated workspaces and are not included in the npm package.

The test suite covers:

* Initializer output completeness.
* Absence of maintainer-only files in generated workspaces.
* Generated `package.json` scripts and dependency visibility.
* Non-empty target rejection and safe `--force` behavior.
* Runtime build outputs and copied assets.
* Removal of each of the seven sample books followed by catalog entry removal.
* Failure on a user-authored real cross-book xref to a missing book.
* Stale HTML directory removal only for books no longer present.
* Runtime clean behavior.
* Official sample contract under `templates/default-workspace/books`.
* npm package boundary content.

The sample contract applies only to `templates/default-workspace/books`.
It verifies that the seven official samples remain present and retain their assigned teaching roles.
It does not apply to generated user workspaces.

== Package Boundary

The npm package `files` field limits the published package to:

[source,json]
----
[
  "dist/",
  "templates/",
  "README.md",
  "CHANGELOG.md",
  "LICENSE"
]
----

The package must include:

* `dist/create.js`
* `dist/init-workspace.js`
* `dist/template-manifest.js`
* `dist/runtime/adoc-books.mjs`
* `templates/default-workspace/package.json.template`
* `templates/default-workspace/gitignore.template`
* `templates/default-workspace/catalog.adoc`
* `templates/default-workspace/books/**`
* `templates/default-workspace/shared/**`
* `CHANGELOG.md`

The package must not include:

* `.github/`
* `test/`
* `src/`
* `DESIGN.adoc`

`pnpm pack --dry-run` is the package boundary evidence surface.
The package boundary test checks required files and forbidden files.

== Maintainer Commands

The maintainer command surface is:

[source,console]
----
pnpm install
pnpm run build
pnpm run test
pnpm run check
pnpm pack --dry-run
----

`pnpm run build` compiles TypeScript to `dist/`.
`pnpm run test` runs `pnpm run build` before executing `node --test test/*.test.mjs`, so tests are valid from a clean tree without `dist/`.
`pnpm run check` runs `pnpm run test` and then `pnpm run pack:check`.
`pnpm run clean` deletes `dist/` and `build/`.

Release notes are maintained in `CHANGELOG.md`.
`release-please-config.json` and `.release-please-manifest.json` configure automated release pull requests.

== GitHub Workflows

CI runs the maintainer check command.

The Release Please workflow opens release pull requests on `main` updates.
Those pull requests update `CHANGELOG.md`, version metadata, and GitHub release state.

The npm publish workflow runs on published GitHub releases.
It installs dependencies, runs `pnpm run check`, and publishes the package to npm with the `NPM_TOKEN` repository secret.

The Pages workflow builds the initializer, creates a temporary default workspace, installs that generated workspace, builds its HTML, and uploads the generated workspace's `build/html` directory.
The Pages workflow does not treat the maintainer repository root as a user workspace.

== Acceptance Criteria

The design is satisfied when these statements are true:

* `pnpm create asciidoc-multi-book-workspace my-books` creates a complete user workspace.
* The generated workspace contains the seven sample books by default.
* The generated workspace does not contain maintainer assets.
* The generated `package.json` directly lists `asciidoctor`, `@asciidoctor/reducer`, and `asciidoctor-kroki`.
* The generated workspace builds with `pnpm install` followed by `pnpm run build`.
* The generated workspace checks with `pnpm run check`.
* Deleting any one official sample book and removing its catalog entries leaves `pnpm run check` passing.
* A user-authored executable xref to a missing book or missing anchor fails the check.
* The user runtime does not use a global Asciidoctor CLI.
* The user runtime does not shell through multiple package-manager subcommands.
* The user runtime does not fetch diagram images during ordinary build/check commands.
* The user runtime preserves existing book HTML output directories for still-present books.
* The user runtime removes stale book HTML output directories for removed books.
* The official sample contract checks `templates/default-workspace/books`.
* `pnpm pack --dry-run` contains release assets and excludes maintainer-only files.

== Documentation Roles

`README.md` describes usage of the npm initializer and the maintainer command surface.
It is included in the npm package.

`templates/default-workspace/README.md` describes actions available inside a generated workspace.
It is copied into generated workspaces.

`DESIGN.adoc` defines the maintainer object and its contracts.
It is not copied into generated workspaces and is not included in the npm package.
