== Abstract

`create-asciidoc-multi-book-workspace` is an npm initializer for complete AsciiDoc multi-book workspaces.
The initializer creates a user-owned workspace with official sample books, a catalog, shared assets, explicit AsciiDoc dependencies, and one editable local build script.

This repository is the maintainer source for that initializer.
It contains TypeScript initializer source, user runtime source, the default workspace template, maintainer tests, the sample contract, and release-boundary checks.

== Object Boundary

=== Published Object

The published npm package is named `create-asciidoc-multi-book-workspace`.
Its command is:

[source,console]
----
pnpm create asciidoc-multi-book-workspace my-books
----

npm users can run:

[source,console]
----
npm create asciidoc-multi-book-workspace@latest my-books
----

The package is an initializer.
It creates files in the target directory and does not remain as a dependency of the generated workspace.

=== Library Entrypoint

Host CLIs can import the package root and call `initWorkspace`.
The host CLI owns command parsing, command names, prompts, logging, and user-facing output.
This package owns the generated workspace files and the target-directory safety rules.

[source,typescript]
----
import { initWorkspace } from "create-asciidoc-multi-book-workspace";

const result = await initWorkspace({ targetDir: "my-books", force: false });
----

`initWorkspace` returns the resolved target directory and the generated package name.
It creates the same default workspace as the published CLI command.

`initSoloWorkspace` takes the same options, returns the same result shape, and creates the <<solo-workspace>>.

=== Generated Workspace

The generated workspace is a standalone AsciiDoc multi-book project.
It contains:

books/06-lower-volume

The generated workspace does not contain maintainer-only files:

[source,text]

The generated workspace owns its local runtime script.
`tools/adoc-books.mjs` is visible, editable, replaceable, and removable by the user.

=== Solo Workspace

The solo workspace is a one-book shelf.
It contains:

[source,text]
----
README.md
catalog.adoc
package.json
.gitignore
tools/adoc-books.mjs
books/01-structured-writing-conventions
shared/attributes.adoc
----

`books/01-structured-writing-conventions` is a byte-for-byte copy of the sample book `07-structured-writing-conventions`.
The number prefix of a book ID is the book's position on its shelf; the sample book is the first and only book of this shelf, so it is shelved as `01`.
The book's content does not reference its own book ID, so the copy needs no edits.

`catalog.adoc` and `README.md` come from `templates/solo-workspace/` and are written for this shelf.
`shared/images/` is not copied because only the default sample catalog uses it.
The other sample books remain in `templates/default-workspace/books/` and are generated only by the default workspace.

The runtime contract check keeps the hand-written catalog honest: if the catalog and `books/` disagree, `pnpm run check` fails.

== Template Workspace Contract

=== Template Source

`templates/default-workspace/` is a complete user workspace template.
It contains the official sample books, `catalog.adoc`, shared assets, the user README, `package.json.template`, and `gitignore.template`.

`package.json.template` renders to the generated `package.json`.
`gitignore.template` is copied to `.gitignore`.
The template keeps that file under a template-specific name because npm drops `.gitignore` files from published packages.

=== Copy Table

`src/template-manifest.ts` defines one copy table per workspace shape: `defaultWorkspaceCopies` and `soloWorkspaceCopies`.
Each table lists `{ from, to }` entries.
`from` is a path under `templates/`; `to` is the path inside the generated workspace.
A table is the complete list of template content its workspace shape receives.
The initializer copies every entry in table order and adds only the rendered `package.json` and `tools/adoc-books.mjs`.

=== User package.json

The generated `package.json` directly lists the AsciiDoc toolchain:

[source,json]
----
{
  "scripts": {
    "build": "node tools/adoc-books.mjs build",
    "check": "node tools/adoc-books.mjs check",
    "clean": "node tools/adoc-books.mjs clean"
  },
  "devDependencies": {

    "asciidoc-abundant-tree": "^0.2.1",

The initializer package is not listed in the generated workspace.
The user can inspect and manage the AsciiDoc dependencies directly.

=== Official Sample Books

The default workspace contains these sample books:

`00-book-anatomy`::
  A complete book-structure specimen covering frontmatter, body structure, parts, and backmatter.

`01-starter-book`::
  A minimal ordinary book suitable as a copying starting point.

`02-multipart-monograph`::
  A single book that demonstrates `part` and `partintro` structure.

`03-technical-book-workflow`::
  A technical writing sample with diagrams, code includes, book-local assets, and shared assets.

`04-reference-manual`::
  A reference-style book with decision tables, path rules, xref patterns, and glossary material.

`05-upper-volume`::
  An independent upper volume with its own book entry and a stable anchor used in examples.

`06-lower-volume`::
  An independent lower volume that demonstrates cross-volume writing conventions by literal example.

`07-structured-writing-conventions`::
  A structured writing conventions specimen covering headings, stable IDs, role tokens, xrefs, rel predicates, and named attributes as source surfaces.

=== Sample Independence

Every default sample book is independently removable.
A user can delete any one `books/<book-id>/` directory, remove the matching entries from `catalog.adoc`, and run:

[source,console]
----
pnpm run check
----

The check must pass after that operation.

Default sample books must not create real incoming cross-book dependencies on each other.
Book-to-book teaching material uses book IDs, paths, prose, or literal examples instead of executable cross-book xref macros.

Catalog links are the workspace navigation surface.
They are the only default links from `catalog.adoc` to sample book entries, and each sample must have catalog entries that can be removed without editing another sample book.

=== Cross-Book Xref Teaching

Cross-book xref syntax is taught as literal source text.
Default samples do not contain executable cross-book xrefs such as:

[source,asciidoc]
----
xref:../other-book/book.adoc#stable-anchor[Target]
----

Instead, samples use separated literal forms such as:

[source,asciidoc]
----
xref + : + ../other-book/book.adoc#stable-anchor[Target]
----

This preserves the teaching surface without creating a real dependency between default samples.

The user runtime still validates real cross-book xrefs.
If a user writes an executable xref to a missing `.adoc` file or missing anchor, `pnpm run check` must fail.

== Initializer Behavior

The initializer accepts one target path.
Missing target arguments print usage and fail.

`--solo` creates the <<solo-workspace>> instead of the default workspace.
Without it, the initializer creates the default workspace.
`--help` prints usage, including both options.

Target handling rules:

* A missing target directory is created.
* An existing empty target directory is used.
* An existing non-empty target directory is rejected by default.
* `--force` overwrites fixed template output paths and does not delete unknown user files.

The initializer copies every entry of the copy table, renders `package.json.template`, copies the built runtime script to `tools/adoc-books.mjs`, and prints:

[source,text]
----
Created AsciiDoc multi-book workspace in <target>

Next:
  cd <target>
  pnpm install
  pnpm run build

Open:
  build/html/index.html
----

The generated package name is derived from the target directory basename and normalized to a safe npm package name.

== User Runtime Contract

=== Commands

`tools/adoc-books.mjs` supports:

[source,console]
----
node tools/adoc-books.mjs build
node tools/adoc-books.mjs check
node tools/adoc-books.mjs clean
----

The generated `package.json` exposes these commands as:

[source,console]
----
pnpm run build
pnpm run check
pnpm run clean
----

=== Workspace Configuration

The runtime reads an optional `adoc-books.config.mjs` at the workspace root.
The file is an ES module whose default export is a plain object.
Without the file, or for a key the object omits, the runtime uses the default.

`rootIndex.redirectTo`, `rootIndex.title`::
  Target and title of `build/html/index.html`.
  Defaults: `catalog.html` and `AsciiDoc Multi-Book Workspace`.

`homeLink.label`, `homeLink.subtitle`::
  Text of the catalog link injected into every book.
  Defaults: `Back to catalog` and `AsciiDoc multi-book workspace`.

`documentRoot`::
  The directory a book's include graph may reach, relative to the workspace root.
  Default: `.`, the workspace root.
  It must be a path string and must contain the workspace root; any other value fails the build instead of falling back to the default.

`includeResolvers`::
  Include resolvers registered by the workspace, in the shape `asciidoc-abundant-tree` accepts.
  Default: none.

Books include `../../shared/attributes.adoc`, so `documentRoot` is never smaller than the workspace root.
A workspace that lives inside a project repository declares the project root, for example `documentRoot: ".."`, so books can include the project's own code instead of keeping a second copy of it.
`documentRoot` is also the base of every source path the reader shows: page source spans, the page map's book entry, and the `// file:` markers of the copied source bundle are relative to it.
Other tools that read the same books, such as structure checks or graph projections, should read `documentRoot` and `includeResolvers` from this file rather than assume the workspace root, so every reader of the books agrees on one root and one set of resolvers.

An include resolver is an object `{ prefix, resolve }`.
An include directive whose target starts with a registered prefix is resolved by that resolver both when Asciidoctor renders HTML and when `asciidoc-abundant-tree` derives the reader data, so both read the same lines.
Prefixes are matched with `startsWith`, so a prefix ends with a separator such as `:`; a prefix `snip` would also claim `include::snippets/x.adoc[]`.
`resolve` runs once per directive on each side, twice per build, and must give the same result both times.

`resolve` receives the target without the prefix, the directive's attributes, and the absolute path of the file that contains the directive.
What the target means is the resolver's own decision; a resolver that wants Asciidoctor's rule, relative to the including file, resolves it against `path.dirname(sourcePath)`.
The attributes have the shape Asciidoctor.js 4 gives include processors: positional attributes keyed by position (`"1"`, `"2"`, ...), named attributes by name, and `opts` expanded to `<name>-option`.
The HTML build runs on Asciidoctor.js 3, which keeps positional attributes in a separate list; the runtime reshapes them so that one resolver serves both sides.
Attribute values are strings; a positional attribute left empty at the start (`[,x]`) is `null` on both sides.
Positional attributes must not be left empty between others (`[a,,b]`): Asciidoctor.js 3 drops the gap and numbers the rest differently from version 4, and the runtime cannot restore it.

`resolve` returns `{ text, origin: { path, startLine } }`: contiguous whole lines of one file, that file's path (absolute, or relative to `documentRoot`), and the 1-based line the text starts at.
The file must lie within `documentRoot`, not be `documentRoot` itself, and must be the real source of the text: the runtime reads it and checks that `text`, without one final line break, equals its lines from `startLine` on, character for character, naming the first line that differs.
The check exists because the two sides use the result differently.
The HTML shows only `text`, while `asciidoc-abundant-tree` records the origin file and puts the whole file into the copied source bundle; an origin that is not the text's source would make the two sides disagree while the build still succeeds.
Asciidoctor messages and reader source spans point at the real lines of that file.

Asciidoctor.js 3 runs include processors synchronously, so `resolve` must return its result directly.
A resolver that returns a Promise, throws, returns another shape, returns lines that are not the origin's lines, or points outside `documentRoot` fails the build with the resolver's prefix and the directive's location.

=== Build Outputs

`build` creates:

[source,text]
----
build/html/index.html
build/html/catalog.html
build/html/books/<book-id>/book.html
build/html/shared/images/
build/html/books/<book-id>/assets/
----

The build renders catalog HTML, renders each book HTML, copies shared images, copies book-local assets, injects a catalog home link and dual reader UI into book HTML, writes the root HTML index, checks local HTML resources, and checks the workspace contract.
The copy-source control embeds an abundant-tree source bundle for the current book. The bundle preserves each participating source file, whole, with its path relative to `documentRoot` instead of pretending to be a single reduced AsciiDoc file.
Default build and check commands do not write expanded ADOC outputs under `build/adoc/`.
Diagram blocks render as Kroki image URLs by default, so ordinary builds do not depend on the Kroki service at build time.
When `ADOC_BOOKS_FETCH_DIAGRAMS=1` is set, the runtime asks Kroki to fetch diagram images into the local HTML output.

`check` runs the same complete validation path as `build`.
It is allowed to rebuild generated outputs.

`clean` deletes `build/` and no source files.

=== Workspace Contract Checks

The runtime checks the current workspace, not the official sample set.
It validates:

* `catalog.adoc` exists.
* Each `books/*/book.adoc` entry has `:doctype: book`.
* Catalog book links point to existing current books.
* Existing current books are listed in the catalog.
* Generated HTML local `href` and `src` resources exist, including the HTML that executable xrefs to other books render to.
* Fragments of local links in generated HTML name IDs that exist in the target HTML.
* Each book's include graph parses within `documentRoot`, and the parse reports no error-level diagnostic.

Xref targets and anchors are judged on the HTML Asciidoctor generates, not by scanning sources.
AsciiDoc can declare an ID as `[#id]`, `[#id.role]`, `[.role#id]`, `[[id]]`, or `[id=id]`, or generate it from a title; only Asciidoctor knows all of these forms, and the HTML it writes carries every ID it assigned.

A book whose include graph cannot be parsed fails the build.
The runtime does not fall back to a cover-only reader page.
A silently degraded reader hides the cause, typically an include that leaves `documentRoot`; the error names it, and the fix is to declare the larger root in `adoc-books.config.mjs`.

The runtime does not require all official sample books to remain present.
The official sample-book set requirement belongs to maintainer tests only.

=== Cheap Performance Rules

The user runtime uses one Node process for the full build.
It renders HTML with Asciidoctor.js 3 in process through the `@asciidoctor/core` factory.
It does not depend on a global `asciidoctor` executable.

The runtime uses `asciidoc-abundant-tree` in process to derive reader page maps and source bundles.
`asciidoc-abundant-tree` 0.2 brings its own Asciidoctor.js 4 and parses asynchronously; the two Asciidoctor versions live side by side without sharing a runtime, because version 4 is plain JavaScript rather than an Opal build.
It loads `asciidoctor-kroki` only when current `.adoc` sources contain supported diagram blocks.
It looks for those blocks in `catalog.adoc` and in the files under `books/`; a diagram block that reaches a book only through an include from elsewhere (shared files, project code, include resolvers) does not trigger loading.
If diagram blocks exist and `asciidoctor-kroki` cannot be loaded, the runtime reports that the workspace contains diagram blocks and needs the Kroki dependency or needs those blocks removed.

The runtime does not implement content hashing, watch mode, deep incremental graphs, or a custom cache system.
It preserves HTML output directories for books that still exist so fetched Kroki SVG files can be reused when `ADOC_BOOKS_FETCH_DIAGRAMS=1` is used.
It deletes HTML output directories for books that no longer exist so removed books do not remain in generated output.

== Maintainer Tests

Maintainer tests are repository-only.
They are not copied into generated workspaces and are not included in the npm package.

The test suite covers:

* Initializer output completeness.
* Absence of maintainer-only files in generated workspaces.
* Generated `package.json` scripts and dependency visibility.
* Non-empty target rejection and safe `--force` behavior.
* Runtime build outputs and copied assets.
* Removal of each official sample book followed by catalog entry removal.
* Failure on a user-authored real cross-book xref to a missing book.
* Failure on a cross-book xref to a missing anchor, and a passing check for cross-book xrefs to IDs declared as `[#id]`, `[#id.role, ...]`, `[.role#id]`, `[[id]]`, `[id=id]`, or generated from a title.
* Failure, naming the book, when a book includes a file outside the default `documentRoot`; a passing build once the workspace declares the project root as `documentRoot`, with reader source paths relative to it.
* One include resolver receiving identical requests from the HTML build and from the reader data, with Asciidoctor.js 4 attribute shape, and the HTML listing holding exactly the lines it returned.
* Failure, naming the prefix and the directive's exact line, when an include resolver returns a Promise (resolving or rejecting), throws, returns another shape, returns lines that are not its origin's lines, or points outside `documentRoot`.
* An empty leading positional attribute arriving as `null` on both sides.
* Rejection of a `documentRoot` that is not a string or does not contain the workspace root.
* Asciidoctor messages inside resolved text reported at the source file's own lines, under the path Asciidoctor uses for its own includes.
* Stale HTML directory removal only for books no longer present.
* Runtime clean behavior.
* Official sample contract under `templates/default-workspace/books`.
* npm package boundary content.

The sample contract applies only to `templates/default-workspace/books`.
It verifies that the official samples remain present and retain their assigned teaching roles.
It does not apply to generated user workspaces.

== Maintainer Commands

The maintainer command surface is:

[source,console]
----
pnpm install
pnpm run build
pnpm run test
pnpm run check
pnpm pack --dry-run
----

`pnpm run build` compiles TypeScript to `dist/`.
`pnpm run test` runs `pnpm run build` before executing `node --test test/*.test.mjs`, so tests are valid from a clean tree without `dist/`.
`pnpm run check` runs `pnpm run test` and then `pnpm run pack:check`.
`pnpm run clean` deletes `dist/` and `build/`.

Release notes are maintained in `CHANGELOG.md`.
`release-please-config.json` and `.release-please-manifest.json` configure automated release pull requests.

== GitHub Workflows

CI runs the maintainer check command.

The Release Please workflow opens release pull requests on `main` updates.
Those pull requests update `CHANGELOG.md`, version metadata, and GitHub release state.

The npm publish workflow runs on published GitHub releases.
It installs dependencies, runs `pnpm run check`, and publishes the package to npm with the `NPM_TOKEN` repository secret.

The Pages workflow builds the initializer, creates a temporary default workspace, installs that generated workspace, builds its HTML, and uploads the generated workspace's `build/html` directory.
The Pages workflow does not treat the maintainer repository root as a user workspace.

== Acceptance Criteria

The design is satisfied when these statements are true:

* `pnpm create asciidoc-multi-book-workspace my-books` creates a complete user workspace.
* The generated workspace contains the official sample books by default.
* The generated workspace does not contain maintainer assets.
* The generated `package.json` directly lists `@asciidoctor/core`, `asciidoc-abundant-tree`, and `asciidoctor-kroki`.
* The generated workspace builds with `pnpm install` followed by `pnpm run build`.
* The generated workspace checks with `pnpm run check`.
* `initSoloWorkspace` creates a workspace whose only book is sample book 07 shelved as `01-structured-writing-conventions`, and that workspace passes `pnpm run check`.
* Deleting any one official sample book and removing its catalog entries leaves `pnpm run check` passing.
* A user-authored executable xref to a missing book or missing anchor fails the check.
* An executable xref to an ID declared in any AsciiDoc form, or generated from a title, passes the check.
* A book that includes a file outside `documentRoot` fails the check; declaring a larger `documentRoot` in `adoc-books.config.mjs` makes it pass, with reader source paths relative to that root.
* An include resolver declared in `adoc-books.config.mjs` resolves its directives for both the HTML and the reader data.
* The user runtime does not use a global Asciidoctor CLI.
* The user runtime does not shell through multiple package-manager subcommands.
* The user runtime does not fetch diagram images during ordinary build/check commands.
* The user runtime preserves existing book HTML output directories for still-present books.
* The user runtime removes stale book HTML output directories for removed books.
* The official sample contract checks `templates/default-workspace/books`.
* `pnpm pack --dry-run` contains release assets and excludes maintainer-only files.
